<dev_only_elimination_finding>
**This was measured during planning with a throwaway sentinel build. Use these commands verbatim —
the obvious variant silently produces a useless control.**

The UI-SPEC's required production check is a *negative* grep:

    npm run build && grep -rl "ee-portfolio-direction" dist/assets/*.js   # expect: no output

A negative grep alone is worthless if the string was never emitted for an unrelated reason (typo in
the key, component never actually imported). It needs a positive control: a build where the string
**is** present. Planning measured three variants against a `import.meta.env.DEV`-gated sentinel:

| Build command | Sentinel in bundle | Usable as control? |
|---|---|---|
| `npx vite build` | absent | no — this is the thing being tested |
| `npx vite build --mode development` | **absent** | **no — `vite build` force-sets `NODE_ENV=production`, so `import.meta.env.DEV` is still `false`. This looks like a control but silently is not.** |
| `NODE_ENV=development npx vite build --mode development` | **present** | **yes — use this** |

So the pair of commands that actually proves dead-code elimination (rather than "the string never
existed") is Task 2's `<verify>`: the control build must FIND the key, and the production build must
NOT find it.

Vite statically replaces `import.meta.env.DEV` with `false` in production, making the gated branch
and its only import unreachable, after which Rollup tree-shakes `DirectionSwitcher.tsx` and its
`directions.ts` import (both are side-effect-free ESM modules).

**Contingency:** if the production grep unexpectedly finds the key, do **not** weaken the check.
Convert the mount in `src/App.tsx` to a `React.lazy(() => import("@/components/DirectionSwitcher"))`
behind the same `import.meta.env.DEV` gate, re-run both builds, and record the deviation in the summary.
</dev_only_elimination_finding>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Build-time source → static bundle | Where dev-only tooling could leak into shipped output. The primary boundary for this plan. |
| `sessionStorage` → DOM attribute | Browser-local, user-writable value read back and applied to `<html>`. Only runtime input in the phase. |

This is a static, backend-less, auth-less site (confirmed in `.planning/codebase/STACK.md` and
`INTEGRATIONS.md`). There is no server, no secret, no network call, and no new dependency in scope.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-04 | Tampering | `src/App.tsx` DEV gate → `dist/assets/*.js` | mitigate | Dev tooling reaching production is the one real risk here. Mitigated by an inline literal `import.meta.env.DEV` gate (statically replaced by Vite, enabling tree-shaking) **and** by a two-build A/B gate in Task 2: a positive control build must contain `ee-portfolio-direction` and the production build must not. The control is required because a bare negative grep passes trivially on a typo'd key and would give false assurance. |
| T-01-05 | Tampering | `DirectionSwitcher` `sessionStorage` read → `setAttribute` | mitigate | The stored value is attacker-controllable via devtools. It is validated against the `DIRECTIONS` allowlist (`DIRECTIONS.some(...)`) before reaching the DOM, falling back to `DIRECTIONS[0].id`. The sink is a `data-*` attribute, not `href`/`innerHTML`/an event handler, so it is not a script-execution sink even unvalidated; allowlisting is defense in depth against CSS-selector confusion. |
| T-01-06 | Information Disclosure | `sessionStorage["ee-portfolio-direction"]` | accept | Stores a non-secret direction id (`"baseline"`), origin-scoped and cleared on tab close. Nothing sensitive to disclose. |
| T-01-07 | Denial of Service | Switcher panel | accept | Dev-only, single `setAttribute` per click, no loops, no network, never shipped. Negligible. |
| T-01-SC | Tampering | npm/pip/cargo installs | mitigate | **Not applicable — this plan installs no packages.** `ui/button.tsx` and its deps are already present and committed. No `package.json` dependency changes are authorized; adding one requires re-planning with a legitimacy audit per the GSD package gate. |

Note: the switcher's reduced touch target (32px vs 44px) is an accepted a11y exception per UI-SPEC
"Spacing Scale", justified precisely because T-01-04 guarantees it never reaches production users.
It is not a security control.
</threat_model>
