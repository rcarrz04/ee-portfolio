# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

> **Scope note:** This phase builds ARCHITECTURE, not a final visual direction. It does not pick colors/fonts for the eventual site — it fixes the routing so Phase 2 can cheaply author and compare 3 candidate directions, and Phase 3 can implement the winner. Every value below marked "baseline placeholder" is deliberately plain/neutral and expected to be overridden or extended by Phase 2, not iterated on for its own sake.

## Token & Switcher Architecture (Phase-1-specific contract)

This is the core deliverable of Phase 1. The four subsections below map 1:1 to TOKEN-01..04.

### 1. Semantic Token Contract (TOKEN-01)

**Do not invent new token names.** The full semantic vocabulary already exists in `src/index.css` (`:root` / `.dark`) and is mapped in `tailwind.config.js` `theme.extend.colors`. Every page/component must resolve color through these Tailwind classes only:

| Semantic role | Tailwind classes | CSS variable(s) |
|---|---|---|
| Base surface / text | `bg-background`, `text-foreground` | `--background`, `--foreground` |
| Card/panel surface | `bg-card`, `text-card-foreground` | `--card`, `--card-foreground` |
| Popover surface | `bg-popover`, `text-popover-foreground` | `--popover`, `--popover-foreground` |
| Primary (highest-emphasis) | `bg-primary`, `text-primary-foreground` | `--primary`, `--primary-foreground` |
| Secondary surface | `bg-secondary`, `text-secondary-foreground` | `--secondary`, `--secondary-foreground` |
| Muted / low-emphasis text | `bg-muted`, `text-muted-foreground` | `--muted`, `--muted-foreground` |
| Accent (sparingly, see Color section) | `bg-accent`, `text-accent-foreground` | `--accent`, `--accent-foreground` |
| Destructive | `bg-destructive`, `text-destructive-foreground` | `--destructive`, `--destructive-foreground` |
| Borders / inputs / focus ring | `border-border`, `border-input`, `ring-ring` (or `ring-offset-*`) | `--border`, `--input`, `--ring` |
| Radius | `rounded-lg` / `rounded-md` / `rounded-sm` | `--radius` |

**Forbidden (must reach zero occurrences by end of Phase 1):** `bg-paper`, `text-paper`, `text-ink`, `bg-ink`, `border-ink`, `text-graphite`, `border-line`, `text-signal`, `border-signal`, `bg-signal` — and the corresponding `paper`/`ink`/`graphite`/`line`/`signal` entries in `tailwind.config.js` `theme.extend.colors` once nothing references them.

**Verified current extent of the problem** (research-time grep, for planner sizing — not a checklist to execute here): hardcoded palette classes currently appear in `src/App.tsx`, `src/components/Navbar.tsx`, `src/components/ProjectCard.tsx`, and all six mounted pages (`Home`, `About`, `Projects`, `ProjectDetail`, `Resume`, `Contact`) — roughly 70+ individual class occurrences across 9 files. `src/pages/Index.tsx` and `src/pages/NotFound.tsx` are unmounted (not in `App.tsx`'s `<Routes>`) — do not spend effort routing their tokens unless the plan decides to also fix/remove that orphan boilerplate (out of this phase's stated scope; flag, don't fix, per `STATE.md`/`STRUCTURE.md` conventions).

**Verification command for TOKEN-01 (grep, zero-match target):**
```bash
grep -rEn "\b(bg|text|border)-(paper|ink|graphite|line|signal)\b" src --include="*.tsx"
```

### 2. Type-Role Contract (TOKEN-03)

Keep the existing three-role structure (`font-display` / `font-body` / `font-mono`) as the permanent role vocabulary in JSX — **never** a literal font-family. What changes is the indirection: today `tailwind.config.js` hardcodes literal font stacks; Phase 1 must route these through CSS variables (same indirection pattern already used for color).

**Before (current — literal, not swappable):**
```js
fontFamily: {
  display: ["'Space Grotesk'", "-apple-system", "sans-serif"],
  body: ["'IBM Plex Sans'", "-apple-system", "sans-serif"],
  mono: ["'IBM Plex Mono'", "ui-monospace", "monospace"],
}
```

**After (required — variable indirection):**
```js
fontFamily: {
  display: ["var(--font-display)"],
  body: ["var(--font-body)"],
  mono: ["var(--font-mono)"],
}
```

**Baseline placeholder values, defined once in `:root` (not per-mode — fonts don't change between light/dark, only between directions in Phase 2):**
```css
:root {
  --font-display: 'Space Grotesk', -apple-system, sans-serif;
  --font-body: 'IBM Plex Sans', -apple-system, sans-serif;
  --font-mono: 'IBM Plex Mono', ui-monospace, monospace;
}
```

This reuses the exact fonts already loaded — visual output is unchanged from today. Phase 2 authors 2 more values-only blocks (e.g. `[data-direction="b"] { --font-display: ...; }`) without touching `tailwind.config.js` or any component again.

The unused `sfpro` fontFamily key is pre-existing dead code, not part of this contract — leave it alone (do not remove without being asked, per surgical-changes convention).

**Verification for TOKEN-03:** `grep -rn "font-family:" src --include="*.tsx"` and `grep -rn "'Space Grotesk'\|'IBM Plex" src/**/*.tsx` should return zero matches (no literal family names inside JSX/`style=` attributes) once done.

### 3. Dark Mode Values — Authored, Not Inverted (TOKEN-02)

This is a real, independently-authored value set required now, not a Phase-2 placeholder — `.dark` is a **mode** (light/dark), orthogonal to the `data-direction` **identity** switcher below. The existing `.dark` block in `src/index.css` is shadcn's untouched Lovable-default scaffold and must be replaced with values chosen specifically for this site's light palette (warm off-white background, orange accent), not a lightness inversion.

**Baseline placeholder dark values (concrete, ready to drop into `.dark`):**
```css
.dark {
  --background: 220 18% 9%;        /* dark charcoal-navy, not pure black */
  --foreground: 40 15% 95%;        /* soft warm off-white, not pure white — echoes light mode's warm undertone */

  --card: 220 16% 13%;             /* +4L over background = elevation step 1 */
  --card-foreground: 40 15% 95%;

  --popover: 220 16% 13%;
  --popover-foreground: 40 15% 95%;

  --primary: 40 15% 95%;
  --primary-foreground: 220 18% 9%;

  --secondary: 220 14% 18%;
  --secondary-foreground: 40 15% 95%;

  --muted: 220 14% 18%;
  --muted-foreground: 220 8% 62%;

  --accent: 19 85% 58%;            /* lightened + slightly desaturated vs light mode's 43% L —
                                       naive reuse of the light accent reads dim on a dark base */
  --accent-foreground: 220 18% 9%;

  --destructive: 0 62% 45%;
  --destructive-foreground: 210 40% 98%;

  --border: 220 14% 22%;
  --input: 220 14% 22%;
  --ring: 19 85% 58%;
}
```

Leave `--radius` and `--sidebar-*` values untouched (sidebar tokens are unused scaffold per `STRUCTURE.md`, not exercised by any mounted page).

**Rationale (per `ARCHITECTURE.md` Pattern 2):** base ~9% lightness (not 0%), 4-point elevation step for `card`/`popover`, off-white foreground instead of pure white, accent hue held constant (19°) but lightness/saturation re-tuned for equal perceived contrast on a dark base rather than reused verbatim from light mode.

**Verification for TOKEN-02:** these are starting authored values, not guaranteed-final — the plan/executor must run an actual contrast check (e.g. browser devtools contrast tool or a WCAG contrast calculator) on `foreground`/`background`, `muted-foreground`/`background`, and `accent-foreground`/`accent` pairs and nudge L by ±3-5 points if any pair fails 4.5:1 (body) / 3:1 (large text). Toggling `.dark` via the existing `ThemeProvider` (already wired, just unexercised — `defaultTheme="light"` in `App.tsx` stays as-is; this phase doesn't add a light/dark toggle UI, it only needs the values to be real when `.dark` is exercised e.g. via devtools or OS preference) must visibly produce a coherent dark page, not a mechanically-inverted one.

### 4. Dev-Only Direction Switcher (TOKEN-04)

**Chosen mechanism:** a `data-direction` attribute on `<html>` (`document.documentElement`), same DOM-attribute pattern the existing `ThemeProvider` already uses for `.dark`/`.light` classes — set via a small floating dev-only panel, not a hidden route or keyboard shortcut (simplest reliable option for repeatedly comparing pages during Phase 2; route/shortcut approaches add navigation/focus complexity with no benefit here).

**New files:**

| File | Responsibility |
|---|---|
| `src/lib/directions.ts` | Exports `DirectionId` type + `DIRECTIONS: { id: DirectionId; label: string }[]` registry array. Phase 1 ships exactly one entry: `{ id: "baseline", label: "Baseline" }`. Phase 2 appends 2 more entries here — no other file needs to change to add a direction to the switcher UI. |
| `src/components/DirectionSwitcher.tsx` | Dev-only floating panel. Renders one small button per `DIRECTIONS` entry (reuse existing `src/components/ui/button.tsx`, `size="sm"`, `variant="outline"`, active entry gets `variant="default"` + `aria-pressed="true"`). On click: `document.documentElement.setAttribute("data-direction", id)` + persist to `sessionStorage`. On mount: reads `sessionStorage.getItem("ee-portfolio-direction")` (fallback to `DIRECTIONS[0].id`) and applies it. |

**Mount point:** `src/App.tsx`, inside the existing wrapper div, as a sibling to `<Toaster />`, gated by `import.meta.env.DEV`:
```tsx
<Toaster />
{import.meta.env.DEV && <DirectionSwitcher />}
```

**Placement/visual:** `fixed bottom-4 right-4 z-50`, small card (`bg-card border border-border rounded-md shadow-md p-2`), label text "Direction" above the button row. Not a production-quality a11y surface (dev-only) — buttons may use a 32px min touch target instead of the usual 44px, gap `8px` between buttons.

**Baseline behavior in Phase 1:** with only one registered direction, no `[data-direction="baseline"]` CSS block is required — `:root` already *is* the baseline values, so selecting "Baseline" is a visual no-op by design. What Phase 1 proves is the plumbing (attribute gets set/read correctly, persists across reload, panel renders in dev and is provably gone in prod) — not a visible palette swap, since there is only one direction until Phase 2. Phase 2 must decide whether to give each new direction (including the dark one) an explicit fully-redefined `[data-direction="x"]` block (recommended, avoids partial-inheritance bugs from `:root`) — that decision is Phase 2's, not this phase's.

**Verifiable production absence — required check, run after implementation:**
```bash
npm run build
grep -ril "ee-portfolio-direction" dist/assets/*.js
```
Expected: no output (exit code 1 / no matches). This greps for the unique `sessionStorage` key string literal rather than the component name, because production minification renames identifiers but never renames string literals — a reliable, minification-proof check that the switcher's code path was fully dead-code-eliminated by Vite (`import.meta.env.DEV` is statically replaced with `false` in production builds, making the gated branch and its only import unreachable and tree-shakeable).

**Explicitly not built in Phase 1** (avoid scope creep per CLAUDE.md simplicity guidance): keyboard shortcut cycling, a dedicated `/directions` route, system-theme-aware defaults for the switcher itself. These are optional future enhancements only if Phase 2 finds the panel insufficient — not required to satisfy TOKEN-04.

## Spacing Scale

Declared values (must be multiples of 4) — unchanged, Layer-1 structural rhythm, constant across all directions per `ARCHITECTURE.md`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact element spacing (e.g. switcher panel internal gap) |
| md | 16px | Default element spacing |
| lg | 24px | Section padding |
| xl | 32px | Layout gaps |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing |

Exceptions: DirectionSwitcher buttons use a 32px min touch target (below the usual 44px) — acceptable because it's a dev-only tool operated with a mouse, never shipped to production, not subject to production a11y targets.

Note: Tailwind's default 4px scale (`tailwind.config.js` — `spacing` key is not overridden) already provides this; Phase 1 does not touch `theme.extend.spacing`.

## Typography

Baseline/inherited — Phase 1 does not change existing font sizes or the type scale (out of scope for TOKEN-01..04, which govern color-token routing, font-family-role binding, and the switcher only). Values below reflect current dominant usage across the 6 mounted pages, captured here so Phase 2's directions have a documented starting scale to vary the *ratio* of, per `ARCHITECTURE.md` Pattern 3 — not a new decision made by this phase.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px (`text-base`) | 400 (regular, default) | 1.5 |
| Label | 12px (`text-xs`) | 500 (medium) | ~1.4 |
| Heading | 30px (`text-3xl`) | 600 (semibold) | 1.2 |
| Display | 48px (`text-5xl`, hero only) | 600 (semibold) | 1.1 |

Weight note: current app pages predominantly use `font-medium` (500) for emphasis (nav links, labels, card titles — 6 files) with `font-semibold` (600) used in exactly 2 places (`Navbar` active link, one `Home` heading). Declaring exactly 2 formal weight roles per the design-contract convention: **400 regular** (body default) and **600 semibold** (headings, via the existing `font-display`/`h1-h4` binding in `index.css`). The pre-existing `font-medium` (500) usage is not required to change for this phase — flag as a minor inconsistency for Phase 2/3 cleanup if a formal weight scale matters to the chosen direction, not a TOKEN-01..04 blocker.

## Color

Expressed as HSL triplets (matches this repo's native token format in `index.css`, not hex) since components never touch hex values directly — only `hsl(var(--x))`.

| Role | Value (`:root` / light) | Usage |
|------|-------|-------|
| Dominant (60%) | `background: 60 17% 95%` (warm off-white) | Page background, default surface |
| Secondary (30%) | `secondary`/`muted: 204 7% 92%`, `card: 60 17% 95%` | Cards, nav bar, secondary panels |
| Accent (10%) | `accent: 19 89% 43%` (orange) | Reserved for: active nav link indicator, primary CTA buttons, `ring`/focus states, the DirectionSwitcher's active-selection button — never a large fill or body text color |
| Destructive | `destructive: 0 84.2% 60.2%` (light) / `0 62% 45%` (dark, re-authored) | Destructive actions only — none exist in Phase 1's own scope, but the token must stay wired for existing shadcn primitives (`alert-dialog`, `toast`, etc.) |

Dark-mode counterpart values are the newly-authored `.dark` block specified in the "Dark Mode Values" subsection above — not repeated here to avoid duplication/drift; that section is the source of truth.

**These are pre-existing values Phase 1 inherits, not new decisions** — Phase 1's job is routing 100% of usage through these names (TOKEN-01), not picking new ones. Phase 2 is where 3 genuinely distinct palettes get authored as `data-direction` value blocks.

## Assumptions & Discretion Notes (for planner/checker)

- **`.dark` vs `data-direction` stay separate mechanisms.** This phase does not make Phase 2's 3 candidate directions toggle via `.dark` automatically — Phase 2 decides per-direction whether "dark/no-motif" is implemented as its own `[data-direction="x"]` block with literal dark-appropriate values, or composed with the existing `.dark` class. Flagged here so the plan doesn't silently conflate the two.
- **`[data-direction="baseline"]` CSS block intentionally omitted in Phase 1** — baseline behavior comes from `:root` alone. If this causes ambiguity for Phase 2 (e.g. needing an explicit block to diff against), Phase 2 can add one trivially; not required now.
- **Weight/size type-scale table above is descriptive, not prescriptive** — Phase 1 does not enforce or rewrite existing size/weight usage on pages; it only fixes the font-*family* role binding (TOKEN-03). Don't let the plan scope-creep into a full type-scale normalization pass.
- **`src/pages/Index.tsx` / `NotFound.tsx`** are unmounted orphans with their own hardcoded Tailwind gray/blue classes (not even the `paper/ink` palette) — explicitly out of this phase's grep/verification target since they're not reachable via any route.
